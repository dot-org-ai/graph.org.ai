# Data Pipelines

Data pipelines are specialized workflows that extract, transform, and load data across systems. They form the backbone of modern data infrastructure and enable organizations to derive insights from disparate data sources.

## Overview

Data pipelines orchestrate the movement and transformation of data at scale. From traditional batch ETL processes to modern real-time streaming systems, data pipelines solve the critical challenge of making data available, clean, and actionable for analysis and applications.

## Pipeline Paradigms

### ETL (Extract-Transform-Load)

**Definition**: Traditional data integration pattern that extracts data from sources, transforms it to meet business requirements, and loads into target systems.

**Architecture**:
```
┌─────────────┐
│  Source 1   │─┐
└─────────────┘ │
                │
┌─────────────┐ │
│  Source 2   │─┼──→ ┌───────────┐     ┌──────────────┐     ┌────────────┐
└─────────────┘ │    │  Extract  │────▶│  Transform   │────▶│   Load     │
                │    └───────────┘     └──────────────┘     └────────────┘
┌─────────────┐ │
│  Source N   │─┘
└─────────────┘

                    ↓ (Data Warehouse)
                ┌────────────┐
                │  Analytics │
                │  Platform  │
                └────────────┘
```

**Characteristics**:
- **Batch-Oriented**: Scheduled runs, often daily
- **Schema-Enforced**: Strict data quality requirements
- **Error Handling**: Validation, reconciliation
- **Audit Trail**: Complete data lineage

**Example (Apache NiFi)**:
```xml
<processor>
  <id>extract-from-source</id>
  <type>GetFile</type>
  <properties>
    <property>
      <name>Input Directory</name>
      <value>/data/source</value>
    </property>
  </properties>
</processor>

<processor>
  <id>transform-data</id>
  <type>ExecuteScript</type>
  <properties>
    <property>
      <name>Script Engine</name>
      <value>python</value>
    </property>
    <property>
      <name>Script File</name>
      <value>transform.py</value>
    </property>
  </properties>
</processor>

<processor>
  <id>load-to-warehouse</id>
  <type>PutSQL</type>
  <properties>
    <property>
      <name>Database Connection Pooling Service</name>
      <value>DBCPService</value>
    </property>
  </properties>
</processor>

<connection>
  <source>extract-from-source</source>
  <destination>transform-data</destination>
</connection>

<connection>
  <source>transform-data</source>
  <destination>load-to-warehouse</destination>
</connection>
```

**Advantages**:
- Mature tooling ecosystem
- Well-understood patterns
- Strong data validation
- Clear audit trails

**Limitations**:
- Latency (batch schedules)
- Upfront schema design required
- Less flexible for exploratory data
- Infrastructure complexity

### ELT (Extract-Load-Transform)

**Definition**: Modern pattern loading raw data first, then transforming within the target system (usually a data warehouse).

**Architecture**:
```
┌─────────────┐      ┌────────────────┐
│  Source 1   │─────▶│ Data Warehouse │
└─────────────┘      │  (Raw Layer)   │
                     └────────┬───────┘
┌─────────────┐              │
│  Source 2   │─────────────▶│
└─────────────┘              │
                     ┌────────▼───────┐
┌─────────────┐      │  Transformation│
│  Source N   │─────▶│   (dbt, SQL)   │
└─────────────┘      └────────┬───────┘
                              │
                     ┌────────▼───────┐
                     │ Analytics Layer│
                     └────────────────┘
```

**Characteristics**:
- **Cloud-Native**: Leverages warehouse compute
- **Schema-on-Read**: Flexible schema evolution
- **SQL-Centric**: Transformation via SQL
- **Version-Controlled**: Code-based transformations

**Example (dbt)**:
```sql
-- models/staging/stg_customers.sql
{{ config(
    materialized='view',
    tags=['daily']
) }}

SELECT
    id,
    email,
    created_at,
    updated_at,
    CASE
        WHEN is_deleted THEN 'deleted'
        WHEN subscription_status = 'active' THEN 'active'
        ELSE 'inactive'
    END as status
FROM {{ source('raw', 'customers') }}
WHERE created_at >= '2024-01-01'


-- models/marts/fact_customers.sql
{{ config(
    materialized='table',
    indexes=[
        {'columns': ['customer_id'], 'type': 'btree'}
    ]
) }}

SELECT
    c.id as customer_id,
    c.email,
    COUNT(o.id) as total_orders,
    SUM(o.amount) as lifetime_value,
    MAX(o.created_at) as last_order_date
FROM {{ ref('stg_customers') }} c
LEFT JOIN {{ ref('stg_orders') }} o ON c.id = o.customer_id
GROUP BY 1, 2
```

**Advantages**:
- Uses warehouse computing power
- Version control for transformations
- Rapid iteration on transforms
- Less infrastructure to manage
- Data democratization

### Streaming Pipelines

**Definition**: Continuous processing of data streams with sub-second latency.

**Architecture**:
```
┌──────────┐      ┌─────────────────┐      ┌──────────┐
│  Event   │─────▶│ Stream Processor │─────▶│  Sinks   │
│ Sources  │      │  (Stateful Ops) │      │ (Store   │
└──────────┘      │                 │      │  Output) │
   (Kafka)        │ - Aggregations  │      └──────────┘
                  │ - Joins         │
                  │ - Windowing     │      (Real-time
                  │ - Filtering     │      Dashboards)
                  └─────────────────┘
                     (Flink/Spark)
```

**Characteristics**:
- **Continuous Processing**: No batch boundaries
- **State Management**: Maintaining aggregates
- **Windowing**: Time-based aggregations
- **Low Latency**: Sub-second processing

**Example (Apache Flink)**:
```java
StreamExecutionEnvironment env =
  StreamExecutionEnvironment.getExecutionEnvironment();

DataStream<Event> eventStream = env.addSource(
  new FlinkKafkaConsumer<>("events", new EventDeserializer(), props)
);

// Stateful aggregation with windowing
DataStream<AggregateResult> results = eventStream
  .keyBy(Event::getUserId)
  .window(TumblingEventTimeWindows.of(Time.minutes(5)))
  .aggregate(new CountAggregator())
  .map(new WindowMapper());

results.addSink(new ElasticsearchSink.Builder<>(
  esConfig,
  new IndexRequestBuilder<AggregateResult>() {
    // ...
  }
).build());

env.execute("Event Processing Pipeline");
```

**Technologies**:
- **Message Brokers**: Kafka, RabbitMQ, AWS Kinesis
- **Stream Processors**: Flink, Spark Streaming, Kafka Streams
- **Sink Connectors**: Elasticsearch, Databases, S3

### Batch Processing

**Definition**: Scheduled processing of large datasets with focus on throughput.

**Architecture**:
```
Schedule Trigger
      │
      ▼
┌──────────────────┐
│ Spark/Hadoop Job │
│                  │
│ • Read Data      │
│ • Distributed Compute
│ • Write Results  │
└────────┬─────────┘
         │
    ┌────▼─────┐
    │ Success? │
    └────┬─────┘
         │
    Yes  │  No
        ▼
    Store Result
    (on failure: retry/alert)
```

**Example (Apache Spark)**:
```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, sum, avg

spark = SparkSession.builder \
    .appName("batch_processing") \
    .getOrCreate()

# Read data
df = spark.read.parquet("s3://data/raw/transactions")

# Transform
result = df \
    .filter(col("amount") > 0) \
    .groupBy("customer_id") \
    .agg(
        sum("amount").alias("total_spent"),
        avg("amount").alias("avg_transaction"),
        count("*").alias("transaction_count")
    ) \
    .filter(col("total_spent") > 1000)

# Write results
result.write \
    .mode("overwrite") \
    .parquet("s3://data/processed/customer_summaries")
```

**Advantages**:
- Cost-effective for large-scale processing
- Mature ecosystem
- Strong consistency guarantees
- Excellent debugging tools

### Lambda & Kappa Architectures

**Lambda Architecture**: Maintains both batch and streaming layers

```
         ┌──────────────────────┐
         │  Real-time Stream    │
         │  Processing Layer    │
         │  (Speed Layer)       │
         └──────────┬───────────┘
                    │
   ┌────────────────┼────────────────┐
   │                │                │
   ▼                ▼                ▼
┌──────────┐   ┌─────────┐    ┌───────────┐
│ Query    │   │ Serving │    │Batch Layer│
│ Results  │   │ Layer   │    │(Batch)    │
└──────────┘   └─────────┘    └───────────┘
   │                │                │
   └────────────────┼────────────────┘
                    │
            ┌───────▼────────┐
            │  Query View    │
            │  (Real + Batch)│
            └────────────────┘
```

**Kappa Architecture**: Single streaming source of truth

```
         ┌──────────────────┐
         │  Event Stream    │
         │  (Source)        │
         └────────┬─────────┘
                  │
         ┌────────▼──────────┐
         │ Stream Processing │
         │ (Flink/Kafka)    │
         └────────┬──────────┘
                  │
      ┌───────────┼──────────┐
      │           │          │
      ▼           ▼          ▼
  Serving   Real-time    Batch
   Store    Analytics    Analytics
```

## Data Quality & Validation

### Schema Validation

```python
# Using Pydantic in Python
from pydantic import BaseModel, validator
from typing import Optional

class Transaction(BaseModel):
    transaction_id: str
    amount: float
    customer_id: int
    timestamp: datetime
    status: str

    @validator('amount')
    def amount_positive(cls, v):
        if v <= 0:
            raise ValueError('Amount must be positive')
        return v

    @validator('status')
    def valid_status(cls, v):
        if v not in ['pending', 'completed', 'failed']:
            raise ValueError('Invalid status')
        return v
```

## Pipeline Orchestration Integration

Data pipelines typically run as [WorkflowEngines.mdx](./WorkflowEngines) tasks:

```typescript
// Temporal workflow orchestrating data pipeline
async function dataIngestWorkflow(
  source: DataSource,
  date: string
): Promise<PipelineResult> {
  const extractedData = await activities.extract(source, date);
  const transformedData = await activities.transform(extractedData);
  const validatedData = await activities.validateQuality(transformedData);
  const loadResult = await activities.load(validatedData, source.target);

  return {
    recordsProcessed: loadResult.count,
    duration: loadResult.duration,
    qualityScore: validatedData.qualityScore
  };
}
```
